# Evaluation: how far the non-LLM pipeline gets (2026-10-24)

Every number below is from a script in this repo. "Simulated" means the signals were generated by a user model
(`simulate.py`), not recorded; conversations marked "real" are held-out turns from DailyDialog, Vertanen's AAC
dialogues or Switchboard. Nothing here is a clinical or user-study result.

## 1. Signals -> intent + referent (simulated, `python simulate.py simulate`)
2 s episodes at 10 Hz; detector misses, false alarms and pointing error by noise level.

| noise | partner context | intent acc | referent acc | hit@1 | hit@3 |
|---|---|---|---|---|---|
| low | on | 0.78 | 0.72 | 0.69 | 0.88 |
| medium | on | 0.65 | 0.50 | 0.59 | 0.74 |
| high | on | 0.60 | 0.38 | 0.52 | 0.72 |

First run, before the "(no message)" intent; silent episodes were scored as hits there, so these overstate.
After the fix, idle is recognized 100% of the time. Intents with no signal (Repeat, and Break when no fist is
seen) are unreachable from video alone. Pointing cannot separate "I want that" from "look at that"; both are
offered.

## 2. What real people reply (`python conversation.py build`)
96,956 real (partner turn -> reply) pairs. Labeled by rules: Yes 15%, No 3.9%, I want 1.4%, Attention 0.4%,
Repeat / Help / Show / Break under 0.1% each, **other 79%** (statements no intent expresses).

## 4. Can the system say what the person actually said?
- **Templates + phrase database vs real AAC messages** (`simulate.py coverage`, 1,500 messages): 10% have a
  close match (cosine >= 0.7).
- **Top-20 retrieved real replies vs the actual reply** (hard-label model, 600 held-out pairs): 29% close.
- **End to end** (`simulate.py dialogue`): 163 real held-out pairs, stratified by reply type. The partner turn
  is real; the user's signals are simulated (medium noise) from what the real reply meant.

| suggestions from | hit@1 | hit@3 |
|---|---|---|
| templates + phrase DB | 0.29 | 0.35 |
| + conversation model | 0.36 | 0.48 |

| real reply type | hit@3 before -> after |
|---|---|
| Yes / No | 0.87 -> 1.00 / 1.00 -> 1.00 |
| Repeat (n=4) | 0.00 -> 0.50 |
| Attention | 0.00 -> 0.20 |
| other (free-form) | 0.00 -> 0.23 |
| I want something (specific requests) | 0.00 -> 0.07 |

### 4b. With an LLM composer (`simulate.py dialogue --llm`, gemma4:cloud through Ollama, same 163 pairs)
| suggestions from | hit@1 | hit@3 | mean best cosine |
|---|---|---|---|
| + conversation model (no LLM) | 0.36 | **0.48** | 0.35 |
| + LLM (3 LLM options) | 0.29 | 0.42 | 0.26 |
| + LLM slot 1, retrieval slots 2-3 | 0.29 | 0.45 | 0.34 |

By type (hit@3, conversation model -> LLM): other 0.23 -> 0.13, I want something 0.07 -> 0.03, Attention
0.20 -> 0.03, Yes/No unchanged at about 1.0. Latency median 2.52 s (p90 2.72 s), 0 failures in 163 calls.
Read: constrained to the frame, the LLM rephrases what Tink already knows. Retrieved real replies sit closer
to what people actually said. This is one model and one prompt, and the test has no scene referents (pointing
or signs), where the LLM's echo-and-specify could matter more. It is not a general verdict on LLMs.

## 5. Enrolled keyword signs (`signs.py check`, one user, one session)
5 signs x 4 takes: leave-one-take-out 20/20. This is optimistic for live use (clean isolated takes); live
spotting with movement between signs is not yet measured.

## 6. Is an LLM needed?
- **Not for the intent level.** Yes/no answers (with the question echoed back), requests about a pointed-at or
  signed object, help, repeat and break all work offline, deterministically and fast.
- **The gap is wording, not intent.** 79% of real replies are free-form statements, and specific requests
  carry content the signals never contain ("a medium Pepsi"). Retrieval reaches about a quarter of free-form
  replies. The rest cannot come from the current signals by any method; there is no information to recover.
- **What an LLM would add** is fluent, specific sentences composed from what is known: the frame (intent,
  referent, modifier), the partner's words and the conversation history. Shown to the user with confirmation,
  this is the pattern the AAC literature supports (SpeakFaster; see `RESEARCH-interpretation.md`). It cannot
  invent facts the user never signalled without hallucinating them, so it must be constrained to the frame
  and always confirmed.
- **Recommendation:** keep the deterministic pipeline as the base, since it is offline and venue-wifi-proof.
  Add an optional LLM composer that only rephrases or specifies within the frame, with a timeout and fallback
  to the current candidates. Measure it with the same `simulate.py dialogue` harness (hit@3 on "other" and
  "I want something" is where it must win) before relying on it in the demo.
